# מנוע ההחלטה V2 — איך מריצים

## הרצה מלאה (מומלץ)
```bash
python3 tools/local_finish_pipeline.py --workdir <PROJ> \
        --director --director-backend chat --render-engine v2
```
דורש ש-`whisper_raw.json` כבר קיים בפרויקט. מנוע ההחלטה רץ **אחרי** התמלול —
מרחב המועמדים נבנה סביב גבולות מילים.

## שלושת ה-backends
| backend | מתי | מה קורה |
|---|---|---|
| `chat` | ברירת מחדל בלי מפתח | כותב כרטיס בקשה ל-`ai_requests/<role>.<digest>.md` ויוצא בקוד 2. שומרים את תשובת ה-JSON ב-`ai_responses/<אותו שם>.json` ומריצים שוב — הצינור ממשיך מאותה נקודה. |
| `api` | יש `ANTHROPIC_API_KEY` | אותה לולאה בדיוק, בלי אדם. מודל: `REL_AI_MODEL`. |
| `replay` | בדיקות, golden, שחזור | קורא **רק** מה-cache. אין תשובה = כישלון רועש, לא ניחוש. |

## חמשת הפאסים
1. **מפיק** → `brief.json` — קהל, מטרה, CTA יחיד, `must_keep`, `off_brief`.
2. **הבנה** → `understanding.json` — קשת סיפור, סיווג כל פאוזה **לפי ראיה נמדדת**,
   סיכוני נטישה. בלי המלצות עריכה.
3. **במאי** → `edit_plan.json` — לכל החלטה: `candidate_id`, פעולה, ביטחון,
   נימוק, ראיה, רווח צפוי, **וחיסרון**. אחר כך validator ואז `edl.json`.
4. **מבקר** → `review.json` — מקבל את התמלול הערוך ומשכי הפערים בפועל,
   **בלי** נימוקים וביטחון. נימוק משכנע גורם לאשר עריכה גרועה.
5. **ציון** → `quality_score.json` — תשעה ממדים, ממוצע משוקלל **מחושב בקוד**
   ולא נלקח מהמודל. מתחת לסף או `blocker` → חזרה לפאס 2 עם focus.

`director_run.json` מסכם: כמה סבבים, ציון סופי, ומאיפה הגיעה כל תשובה.

## ספי ביטחון
`≥0.85` מוחל אוטומטית · `0.60–0.84` מוחל ומסומן להכרעה · `<0.60` מסומן בלבד.

## מה אסור
* `tighten_to` מתחת ל-0.20ש — האוויר מתחלק לשני צידי החיתוך.
* הסרת תוכן לא מוצהרת — חיתוך שמכיל מילים שלמות חייב `action="cut"` על
  `sentence_span` או `t_start`/`t_end` מפורשים.
* מטא-דאטה משתנה ב-payload של פאס (חותמת זמן, מזהה ריצה, שם תיקייה) —
  הורס את יציבות ה-cache.
